# 01 — Видение продукта и продуктовые инварианты

## Назначение

PPM помогает 5–20 проектным командам не только вести задачи, но и удерживать смысл проекта: требования, решения, материалы, код, зависимости и историю обсуждений в одном пространстве.

## Проблема пользователя

Обычный task tracker отвечает на вопрос «кто и что должен сделать», но не связывает в одном контексте:

- задачи;
- документы и файлы;
- объяснения и решения;
- результаты исследований;
- код, commits и pull requests;
- причинные и смысловые связи;
- накопленную память команды.

В результате проект распадается между трекером, папками, чатами, облачными дисками, IDE и Git-провайдером. PPM должен собрать эти источники без копирования их предметной логики.

## Целевые пользователи

- руководитель проектной школы;
- руководитель команды;
- участник команды;
- эксперт или наблюдатель с доступом на чтение;
- разработчик, работающий через VS Code или Codex;
- администратор экземпляра;
- AI-агент, действующий от имени конкретного пользователя и только в разрешённом проекте.

## Основные ценности

1. **Единая рабочая среда.** Проекты, задачи, знания, визуальный контекст и код связаны.
2. **Проектная память.** Ответы строятся на материалах конкретного проекта и сопровождаются источниками.
3. **Визуальное понимание.** Команда видит не только список задач, но и связи между проблемами, решениями и результатами.
4. **Переносимые знания.** Markdown и файлы можно выгрузить и открыть вне PPM.
5. **Стандартная разработка.** Git остаётся Git: обычные clone, branch, commit, push и pull request.
6. **Безопасная автоматизация.** AI предлагает изменения, человек их подтверждает.
7. **Собственная идентичность.** Пользователь воспринимает систему как AntyFlow/PPM, а не как переименованный Plane.

## Четыре рабочих пространства проекта

### 1. Работа

Задачи, статусы, исполнители, сроки, циклы, модули, представления и аналитика. Реализуется на базе Plane.

### 2. Мозг проекта

Бесконечный холст с проекциями задач, страниц, файлов, кода и AI-выводов. Хранит визуальные и семантические связи.

### 3. Знания

Project Vault с папками и файлами плюс штатные Plane Pages в едином интерфейсе. Vault рассчитан на Markdown, документы, изображения, таблицы, презентации и другие проектные материалы.

### 4. Код

Репозитории, ветки, commits, pull requests, проверки и связь с Work Items. Git provider остаётся владельцем Git-объектов.

## Продуктовые инварианты

### I1. Один объект — один источник истины

- Work Item существует в Plane;
- Vault-файл существует в Project Vault;
- Page существует в Plane Pages;
- commit и pull request существуют в Git provider;
- canvas shape содержит ссылку и визуальные свойства.

### I2. Проекция не является копией

Карточка задачи на холсте может появляться несколько раз, но всегда ссылается на один `work_item_id`. Удаление карточки не удаляет Work Item.

### I3. Индекс можно пересобрать

RAG хранит производные chunks и vectors. Потеря индекса не должна приводить к потере исходных файлов, страниц или задач.

### I4. Права проверяются на сервере

`workspace_id`, `project_id` и `entity_id` из URL или браузера не являются доказательством доступа.

### I5. AI показывает основания

Фактическое утверждение в ответе должно иметь ссылку на Work Item, Page, Vault file, canvas node или Git object.

### I6. Запись требует подтверждения

Создание или изменение задач, страниц, Vault-файлов, связей, веток и pull requests проходит через preview и approve. Исключения возможны только для явно настроенной безопасной автоматизации.

### I7. Ручная работа не зависит от AI

При отключённой модели пользователь продолжает создавать задачи, работать с холстом, редактировать Markdown и пользоваться Git.

### I8. Plane не виден как продукт

В пользовательских маршрутах отсутствуют логотип, название, фирменные цвета и продуктовые тексты Plane. Юридическая информация доступна отдельно в разделе open source notices.

### I9. Стандартные форматы важнее lock-in

- Markdown остаётся Markdown;
- Git остаётся стандартным remote;
- экспорт Canvas имеет документированную JSON-схему;
- файлы можно выгрузить без проприетарного клиента.

### I10. Многокомандность проверяется отрицательными тестами

Система считается безопасной только если доказано, что пользователь другой команды не может прочитать project, canvas, Vault, RAG chunks, agent results и Git metadata.

## Не является целью первого релиза

- собственная реализация Git protocol;
- полноценная замена GitHub Actions;
- автономный AI с правом массовой записи;
- offline-first web-приложение;
- синхронное совместное редактирование каждого типа офисного файла;
- обучение отдельной foundation model для каждого проекта;
- полная замена всех редких admin-экранов Plane за два дня;
- production SLA и сертифицированный security audit.

## Метрики полезности

- новый пользователь за 15 минут создаёт проект, задачу, Vault-заметку и связывает их на холсте;
- запрос «что блокирует проект?» возвращает ответ со ссылками на источники;
- commit с ключом задачи связывается с ней без ручного копирования URL;
- команда может экспортировать Vault и открыть Markdown-файлы вне PPM;
- пользователь другой команды не получает ни одного чужого фрагмента в RAG-ответе;
- основные экраны не содержат визуальной идентичности Plane;
- отключение Project Brain не ломает работу задач и файлов.
