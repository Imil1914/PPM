# 02 — Информационная архитектура и пользовательские пути

## Глобальная навигация

```text
PPM
├── Главная
├── Проекты
├── Мои задачи
├── Входящие
├── Поиск
├── Портфель                         после MVP
└── Настройки пространства
```

Названия могут быть уточнены дизайн-системой, но пользователю не показываются внутренние термины `Plane`, `issue` и `workspace slug`.

## Навигация внутри проекта

```text
Проект
├── Обзор
├── Мозг проекта                    Canvas + Graph + Ask
├── Работа
│   ├── Задачи
│   ├── Представления
│   ├── Этапы                       Plane Cycles
│   └── Направления                 Plane Modules
├── Знания
│   ├── Файлы                       Project Vault
│   ├── Совместные страницы         Plane Pages
│   └── Граф знаний
├── Код
│   ├── Репозитории
│   ├── Ветки и commits
│   └── Pull requests
├── Аналитика
└── Настройки проекта
```

`Мозг проекта` становится экраном по умолчанию при повторном входе в уже настроенный проект. При первом входе открывается короткий onboarding, который предлагает создать задачу, добавить материал и поместить их на холст.

## Первый вход

### Шаг 1. Регистрация

Пользователь видит форму PPM. Технически используется auth Plane, но:

- отсутствует бренд Plane;
- русский язык включён по умолчанию;
- юридические ссылки ведут на PPM terms/privacy и отдельный список open source licenses;
- после входа не возникает второй регистрации Canvas, Vault или Git.

### Шаг 2. Пространство

Пользователь создаёт пространство проектной школы или принимает приглашение. На экране объясняется, что пространство объединяет несколько команд и проектов.

### Шаг 3. Проект

Пользователь создаёт project, задаёт название, ключ и видимость. В фоне создаются:

- Plane project;
- пустой Canvas;
- корень Project Vault;
- конфигурация Project Brain;
- пустой Git-контур без repository connection.

Операция идемпотентна: повторный запрос не создаёт дубликаты расширений.

### Шаг 4. Первое полезное действие

Пользователь выбирает один из путей:

- создать задачу;
- загрузить файл;
- создать Markdown-заметку;
- открыть Мозг проекта.

## Сценарий A — задача и холст

1. Пользователь создаёт задачу `ROBOT-12` в разделе «Работа».
2. Открывает «Мозг проекта».
3. Нажимает `Добавить → Задача`.
4. Выбирает `ROBOT-12` из поиска текущего проекта.
5. На холсте появляется проекция задачи.
6. Изменение статуса на карточке вызывает Plane API.
7. Повторное открытие задачи в разделе «Работа» показывает новый статус.
8. Удаление shape удаляет только проекцию.

## Сценарий B — Vault и холст

1. Пользователь открывает `Знания → Файлы`.
2. Создаёт папку `Исследования`.
3. Создаёт `Исследования/Обзор.md` либо загружает PDF.
4. Включает `Индексировать в Мозге проекта` для файла или папки.
5. Перетаскивает файл на холст.
6. Появляется нода с названием, типом, состоянием индекса и ссылкой на источник.
7. Двойной клик открывает редактор/просмотрщик в PPM.

## Сценарий C — вопрос к проекту

1. Пользователь выделяет задачу, документ и две связанные ноды.
2. Нажимает `Спросить проект`.
3. Система формирует область запроса: выбранные ноды → соседи графа → поиск по проекту.
4. Hybrid RAG возвращает фрагменты только разрешённого проекта.
5. Модель создаёт ответ с кликабельными citations.
6. Ответ можно сохранить как AI-ноду, превратить в черновик Page или создать предложения Work Items.
7. Любое действие записи требует подтверждения.

## Сценарий D — код из VS Code или Codex

1. Руководитель связывает Git repository с проектом.
2. Разработчик копирует стандартный HTTPS/SSH clone URL.
3. Открывает repository в VS Code или Codex.
4. Создаёт branch `ROBOT-12/sensor-calibration`.
5. Делает commits с ключом `ROBOT-12`.
6. Выполняет обычный push.
7. Git provider присылает подписанный webhook.
8. PPM связывает branch/commits с Work Item.
9. Созданный pull request появляется в разделах «Код», в задаче и как доступная нода холста.
10. После merge статус виден в PPM; автоматическое закрытие Work Item включается только отдельной настройкой.

## Сценарий E — руководитель проекта

1. Открывает «Мозг проекта».
2. Запускает запрос `Покажи блокировки, неподтверждённые требования и задачи без результата`.
3. Получает сгруппированный ответ со ссылками.
4. Агент предлагает зависимости и новые задачи.
5. Руководитель просматривает diff действий.
6. Подтверждает выбранные действия.
7. Plane создаёт или обновляет Work Items; Canvas добавляет утверждённые связи.

## Пустые и ошибочные состояния

Каждый экран обязан отвечать на три вопроса:

1. Что это за раздел?
2. Что пользователь должен сделать первым?
3. Почему действие недоступно, если оно заблокировано?

Минимальные состояния:

- project ещё не создан;
- Canvas пуст;
- Vault пуст;
- модель не настроена;
- индекс ещё строится;
- источник удалён;
- Git provider не подключён;
- нет прав;
- внешняя система временно недоступна;
- индекс устарел;
- конфликт одновременного редактирования.

## Требования user-friendly

- создание объекта доступно максимум за два понятных действия из его раздела;
- переход из проекции к источнику — один клик/двойной клик;
- источник истины явно обозначается в меню объекта;
- пользователь видит состояние `сохранено / сохраняется / конфликт / ошибка`;
- опасные действия имеют preview последствий;
- технические UUID, имена сервисов и внутренние ошибки не показываются;
- все основные действия доступны с клавиатуры;
- русские термины едины во всех разделах;
- мобильный интерфейс допускает просмотр и простые изменения, но полноценный Canvas ориентирован на desktop/tablet.
