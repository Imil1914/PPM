# G2.1 — ADR и внедрение self-hosted Git provider

## Пользовательский результат

При подтверждённой потребности организация получает собственный Git-контур под своим управлением, а PPM подключает его через тот же provider contract, не реализуя Git-сервер самостоятельно.

## Зависимости

- G1.2 accepted;
- доказана потребность в self-hosting;
- назначены владельцы инфраструктуры, безопасности и резервного копирования;
- проведена отдельная лицензионная и эксплуатационная проверка кандидата.

## Scope

- ADR: внешний managed provider против self-hosted provider;
- сравнительная проверка кандидатов, включая Forgejo/GitLab CE при актуальности на момент решения;
- требования к SSO, repository, protected branches, pull/merge requests, webhooks, API, audit, backup и upgrade;
- threat model и capacity estimate;
- пилот отдельного self-hosted provider;
- новый adapter без изменения базовой PPM-модели;
- migration/rollback plan;
- runbook backup/restore/upgrade;
- приёмочное восстановление из резервной копии.

## Не входит

- разработка собственного Git protocol, object store или merge engine;
- бесшовная миграция всех repositories до успешного пилота;
- обещание полной функциональной идентичности GitHub;
- изменение провайдера без решения владельца и окна миграции.

## Порядок реализации

1. Собрать измеримые требования и причины self-hosting.
2. Сверить актуальные возможности, лицензии и эксплуатационные требования кандидатов по первичным источникам.
3. Оформить ADR с вариантами, стоимостью, рисками и rollback.
4. Получить решение владельца.
5. Поднять изолированный пилот с тестовыми данными.
6. Реализовать adapter, webhook validation и SSO integration.
7. Проверить backup/restore, upgrade и отказоустойчивость.
8. Провести security review и нагрузочный тест.
9. Выполнить ограниченную миграцию одной команды.
10. Только после приёмки расширять rollout.

## Критерии приёмки

1. Есть утверждённый ADR с фактами, а не предположениями о кандидате.
2. Стандартные `clone`, `fetch`, `push`, branch и pull/merge request workflows работают из VS Code и Codex.
3. PPM получает события через общий provider contract.
4. Backup восстановлен в отдельном окружении с проверкой repositories, metadata и доступа.
5. Пилот выдерживает заявленную нагрузку и модель отказа.
6. Rollback к предыдущему provider документирован и проверен на тестовой команде.
7. Пользовательский интерфейс PPM не зависит от конкретного бренда Git provider.

## Проверки

- protocol interoperability;
- provider API/webhook contract;
- SSO/RBAC/audit;
- backup/restore drill;
- upgrade rehearsal;
- capacity/load;
- migration and rollback rehearsal;
- legal/license checklist.

## Rollback

Остановить rollout, вернуть тестовую команду на прежний provider по migration map и сохранить пилот только для расследования. Удаление пилота выполняется отдельным явно подтверждённым действием.
