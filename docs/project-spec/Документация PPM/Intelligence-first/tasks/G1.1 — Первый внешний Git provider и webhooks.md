# G1.1 — Первый внешний Git provider и webhooks

## Пользовательский результат

Пользователь подключает поддерживаемый Git-провайдер к проекту и видит в PPM актуальные ветки, коммиты и pull/merge requests без передачи пароля от Git-аккаунта.

## Зависимости

- G0.1 accepted;
- выбран первый provider и оформлен ADR;
- [../10 — Git и контур разработки](<../10 — Git и контур разработки.md>);
- [../13 — Безопасность, права и изоляция](<../13 — Безопасность, права и изоляция.md>).

## Scope

- один provider adapter: GitHub либо GitLab;
- OAuth или GitHub App/provider app flow;
- шифрованное хранение installation/access credentials;
- выбор доступного repository и связь с project;
- минимальные read permissions;
- webhook endpoint, проверка подписи и защита от replay;
- идемпотентная обработка push и pull/merge request событий;
- синхронизация repository, branch, commit и pull request metadata;
- связь Work Item по ручной ссылке и ключу в branch/commit/PR;
- reconciliation job на случай потерянного webhook;
- audit и отзыв подключения.

## Не входит

- hosting Git repositories внутри PPM;
- browser-based IDE;
- выполнение произвольного кода;
- force push, merge и изменение protected branches;
- несколько provider adapters в одной задаче;
- полнотекстовая индексация исходного кода.

## Порядок реализации

1. Зафиксировать ADR с первым provider и минимальными permissions.
2. Реализовать provider interface и первый adapter.
3. Добавить installation/connect flow и безопасное хранение секретов.
4. Реализовать repository picker и project binding.
5. Поднять подписанный webhook endpoint.
6. Нормализовать события в PPM-модель.
7. Реализовать идемпотентный consumer и reconciliation.
8. Показать commits и pull requests в разделе `Код` и Work Item.
9. Добавить disconnect/revoke и аудит.
10. Прогнать сценарий VS Code/Codex: branch → commit → push → PR → связь с тикетом.

## Критерии приёмки

1. Подключение не требует хранения пользовательского пароля или личного SSH-ключа.
2. PPM запрашивает только документированные минимальные permissions.
3. Подписанный webhook обновляет commit/PR metadata не более одного раза.
4. Повтор одного события не создаёт дубликатов.
5. Branch/commit/PR с ключом Work Item связывается с ним автоматически или попадает в очередь подтверждения по утверждённому правилу.
6. Потерянный webhook восстанавливается reconciliation job.
7. После revoke новые API-вызовы provider недоступны, а исторические ссылки остаются читаемыми согласно retention policy.
8. Пользователь видит понятное состояние подключения и последней синхронизации.

## Проверки

- OAuth/app install happy path и отказ;
- encrypted secret storage и secret redaction;
- webhook signature/replay/idempotency;
- rate-limit/backoff;
- repository permission changes;
- reconciliation после пропущенного события;
- disconnect/revoke;
- E2E branch/commit/PR flow.

## Rollback

Отключить provider feature, отозвать credentials и остановить consumers. Существующие canonical URLs и ручные связи из G0.1 сохраняются.
