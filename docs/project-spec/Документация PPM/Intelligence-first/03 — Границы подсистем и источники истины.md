# 03 — Границы подсистем и источники истины

## Цель

Не допустить появления двух трекеров задач, двух файловых хранилищ одного назначения, двух систем ролей или двух независимых копий кода.

## Матрица ответственности

| Объект | Источник истины | Что хранит PPM дополнительно |
|---|---|---|
| пользователь, сессия | Plane | UI preferences PPM |
| workspace, membership | Plane | onboarding state |
| project, project role | Plane | Brain/Vault/Git configuration |
| Work Item, status, priority, assignee | Plane | canvas bindings, AI proposals |
| cycle, module, saved view | Plane | canvas projection |
| комментарий и activity задачи | Plane | citation/preview cache |
| Plane Page | Plane | индекс, canvas binding |
| attachment Work Item/Page | Plane object storage | индекс и preview metadata |
| Vault folder/file | Project Vault | индекс, backlinks, versions |
| положение и стиль ноды | PPM Canvas | canonical Canvas data |
| смысловая связь нод | PPM Graph | canonical semantic edge |
| RAG chunk/vector | Project Brain | производный rebuildable index |
| вопрос, ответ, agent run | PPM Agents | canonical audit/history |
| repository/branch/commit/PR | Git provider | metadata cache и links |
| Git credentials | secret store/provider | opaque connection reference |

## Plane Pages и Project Vault

Они остаются разными типами, но показываются в одном разделе «Знания».

### Plane Page используется, когда

- документ должен совместно редактироваться в rich-text режиме;
- документ тесно связан со штатным процессом Plane;
- важны встроенные комментарии/возможности Pages;
- пользователю не нужен физический `.md`-файл.

### Vault file используется, когда

- нужен реальный файл и папочная структура;
- материал должен выгружаться и открываться в Obsidian/VS Code;
- это PDF, DOCX, PPTX, таблица, изображение, код или Markdown;
- нужны wiki-links, backlinks и файловый граф;
- материал поступил извне и должен сохраняться без преобразования.

### Запрещённая модель

Нельзя автоматически создавать скрытую копию каждой Plane Page в Vault и считать обе редактируемыми. Если реализуется экспорт Page → Markdown или импорт Markdown → Page, операция должна явно показывать направление и создавать provenance link.

## Plane attachments и Vault files

- вложение комментария/Work Item остаётся attachment Plane;
- файл библиотеки проекта остаётся Vault file;
- действие `Добавить в Vault` создаёт отдельный осознанный объект и фиксирует происхождение;
- обычная проекция attachment на Canvas не копирует файл;
- одинаковый content hash может использоваться для дедупликации физического blob, но логические объекты сохраняют независимые права и историю.

## Board Plane и Canvas

### Plane Board

- Kanban по статусам;
- сортировка и фильтрация;
- массовые действия над Work Items;
- планирование и исполнение.

### PPM Canvas

- свободное пространственное размещение;
- объясняющие и причинные связи;
- совместное расположение задач, документов, файлов и кода;
- AI-контекст выбранных объектов;
- карты решений и архитектурные схемы.

Самостоятельные Kanban и backlog из desktop AntyFlow не включаются в PPM web mode. Допустим только `Work Items View node`, который отображает живую выборку Plane без собственной базы карточек.

## Project Brain и источники

Project Brain не становится источником фактов. Он хранит:

- нормализованные документы индекса;
- chunks;
- embeddings;
- ссылки на источник и его версию;
- результаты retrieval;
- историю запросов и предложений.

Если исходный объект изменён или удалён, его индекс помечается устаревшим и перестраивается/удаляется.

## Git provider и PPM

PPM не хранит Git objects и не выполняет роль remote server в фазах G0–G1. Он хранит:

- connection metadata;
- repository metadata;
- последнюю синхронизацию;
- связи Work Item ↔ branch/commit/PR;
- нормализованные webhook events;
- разрешённый индекс кода и документации.

В режиме G2 bundled Forgejo сам остаётся Git provider. PPM предоставляет собственную оболочку и SSO, но не подменяет его внутреннюю Git-реализацию.

## Правила проекций

1. Shape содержит `entity_type`, `entity_id`, `project_id` и визуальные свойства.
2. Отображаемые бизнес-поля читаются из источника.
3. Допустим краткоживущий cache с `source_version`/`updated_at`.
4. Изменение бизнес-поля вызывает API источника.
5. Удаление shape удаляет только shape и binding.
6. Удаление источника выполняется отдельной командой с подтверждением.
7. Один источник может иметь несколько shapes на одном или разных canvases разрешённого проекта.
8. Cross-project binding отклоняется, если нет явно разрешённого портфельного canvas.

## Проверка нового функционала на дублирование

Перед добавлением любой функции разработчик отвечает:

1. Какой пользовательский объект появляется?
2. Где его единственный источник истины?
3. Почему нельзя использовать существующий объект Plane/Vault/Git provider?
4. Что произойдёт при удалении проекции?
5. Как объект индексируется?
6. Как проверяются права?
7. Можно ли восстановить производные данные из источника?

Если ответы не определены, задача не переходит в `ready`.
