# 02 — Роли и пользовательские сценарии

> Историческая редакция v1. Актуальное ТЗ: [Plane-first/README](<Plane-first/README.md>).

## Роли MVP

| Роль | Область | Возможности |
|---|---|---|
| Владелец пространства | всё пространство | команды, пользователи, все проекты, экспорт, настройки |
| Руководитель команды | одна команда | состав команды, проекты, тикеты, документы, отчёты |
| Участник | назначенные команды | чтение проекта, создание и изменение тикетов и документов |
| Наблюдатель | назначенные проекты | только чтение и выгрузка разрешённых данных |

Администратор инфраструктуры не является продуктовой ролью и не должен автоматически читать содержимое всех проектов через клиентское приложение.

## Матрица доступа

| Действие | Владелец | Руководитель | Участник | Наблюдатель |
|---|---:|---:|---:|---:|
| Создать команду | да | нет | нет | нет |
| Управлять составом своей команды | да | да | нет | нет |
| Создать проект | да | да | нет | нет |
| Создать/изменить тикет | да | да | да | нет |
| Менять статус своего тикета | да | да | да | нет |
| Создать/изменить документ | да | да | да | нет |
| Загрузить файл | да | да | да | нет |
| Запустить агента | да | да | да | нет |
| Подтвердить массовые действия агента | да | да | нет | нет |
| Смотреть проект | да | да | да | да |

## Сценарий A — запуск команды

1. Владелец регистрируется и создаёт пространство проектной школы.
2. Создаёт команду, назначает руководителя и участников.
3. Руководитель создаёт проект из пустого шаблона.
4. Система создаёт доску с пятью статусами и стартовый документ «Паспорт проекта».
5. Команда видит только свои проекты и материалы.

## Сценарий B — ежедневная работа

1. Участник открывает доску.
2. Создаёт тикет с названием, описанием, приоритетом, исполнителем и сроком.
3. Прикрепляет документ или файл.
4. Перетаскивает тикет между статусами.
5. Каждое существенное изменение фиксируется в `activity_events`.

## Сценарий C — документы и файлы

1. Участник создаёт Markdown-документ в проекте.
2. Связывает его с тикетом.
3. Загружает исходный файл в приватное хранилище проекта.
4. Другой участник команды открывает документ и скачивает файл.
5. Наблюдатель может читать, но не менять материал.

## Сценарий D — работа агента

1. Пользователь запускает «Сводку проекта».
2. Агент получает только доступные пользователю тикеты и документы.
3. Результат показывается как черновик с перечнем источников.
4. Пользователь сохраняет его новым документом или отклоняет.
5. Любое сохранение от имени агента записывается в журнал действий.

## Сценарий E — выгрузка руководителю

1. Руководитель выбирает команду или проект.
2. Выгружает CSV с тикетами.
3. Генерирует Markdown-сводку: прогресс, готово, в работе, блокировки, следующие шаги.
4. Файл можно передать вне PPM без доступа к системе.

## Что такое «командный лист» в PPM

Термин фиксируется как два связанных представления:

- **состав команды** — участники, роли и активные проекты;
- **рабочий список** — фильтрованный список тикетов команды по проекту, исполнителю, статусу или сроку.

Отдельную сущность `team_list` в MVP не создаём: состав хранится в memberships, рабочие списки строятся как представления тикетов.
