# AntyFlow Materials R&D: правила исполнения заданий Codex

**Статус:** проект правил; активируется после согласования владельцем  
**Назначение:** превратить backlog в безопасную последовательность небольших реализаций

## 1. Что получает Codex

Codex не получает команду «реализуй весь материаловедческий оркестратор». Он получает одну карточку `Mx.y`, перечисленные в ней спецификации и критерии приёмки.

Канонический источник документации:

```text
docs/materials-orchestrator/
```

Obsidian является точной копией для чтения. При расхождении источником истины считается репозиторий.

## 2. Порядок чтения перед первой задачей

1. `CLAUDE.md` — правила существующего проекта.
2. `docs/materials-orchestrator/README.md`.
3. `03-mvp-scope-and-gap-map.md`.
4. Только необходимые для задачи разделы `04–08`.
5. Текущая task card.
6. Затрагиваемые исходные файлы и существующие тесты.

Не нужно загружать весь корпус литературы или весь справочник переходов для простой инфраструктурной задачи.

## 3. Нормативные правила работы

1. Сохранять существующий generic-оркестратор и обратную совместимость.
2. Добавлять профиль `materials_rnd`, пока отдельный ADR не разрешит другое.
3. Не подключать управление физическим оборудованием.
4. Не менять архитектурные границы без отдельного решения владельца.
5. Использовать Zod для runtime-валидации новых TypeScript-структур.
6. Использовать JSON Schema как внешний контракт.
7. Использовать Pydantic только на границах отдельного Python-сервиса.
8. Не вызывать инструмент, которого нет в ToolSpec registry.
9. Не давать агенту создавать другого агента или менять граф напрямую.
10. Не публиковать научный факт без происхождения.
11. Не подменять отсутствие модели ответом LLM.
12. Не использовать константный LLM confidence как UQ.
13. Не обходить Human Gate 1 и Human Gate 2.
14. Не изменять несвязанные пользовательские файлы.
15. Не удалять пользовательские данные при миграции; сначала создавать восстановимую копию по правилам проекта.
16. Каждый внешний IPC payload валидировать в main.
17. Каждое изменение сопровождать тестом и документацией.
18. Если acceptance criterion нельзя проверить, остановиться и назвать конкретный блокер.

## 4. Рабочий цикл одной задачи

```text
прочитать task card
 → проверить зависимости и рабочее дерево
 → зафиксировать исходный baseline
 → реализовать минимальное изменение
 → выполнить локальные тесты
 → выполнить общий test/build
 → проверить generic regression
 → обновить changelog и task status
 → выдать отчёт
```

Codex не начинает следующую карточку автоматически, если текущая не прошла acceptance или требует решения владельца.

## 6. Статусы карточки

| Статус | Смысл |
|---|---|
| `draft` | Требование ещё уточняется |
| `blocked` | Есть внешний или человеческий блокер |
| `ready` | Зависимости и критерии определены |
| `in_progress` | Codex выполняет задачу |
| `review` | Реализация готова, ожидает проверки |
| `accepted` | Приёмка пройдена |
| `rejected` | Требуется новая реализация или пересмотр ТЗ |
| `superseded` | Карточка заменена новой версией |

## 6.1. Baseline gate после M0.6

Начиная с M1.1, фраза «это старая TypeScript-ошибка» допустима только при точном совпадении с [normative M0.6 manifest](./baselines/M0.6-quality-baseline.json).

Обязательное правило каждой карточки:

1. `npm test` запускает автоматический baseline guard.
2. Fingerprint — нормализованные project-relative file, TS code и primary message; line/column информационные.
3. Новый fingerprint или увеличение количества — регрессия, а не baseline.
4. Исчезновение разрешённой ошибки требует удалить или уменьшить запись manifest в той же карточке; иначе guard намеренно остаётся красным.
5. Добавлять разрешённые ошибки в обычной implementation-карточке запрещено.
6. Смена TypeScript или `tsconfig.json` требует отдельного пересмотра baseline.
7. Падающие tests/build никогда не оформляются как допустимый baseline.

Человекочитаемый снимок и процедура находятся в [инженерном baseline](./10-engineering-quality-baseline.md).

## 8. Пример первой готовой карточки

### `M0.1 — WorkflowProfile`

**Цель:** создать единое runtime-проверяемое определение профиля без изменения текущего поведения.

**Обязательно прочитать:**

- `CLAUDE.md`;
- `03-mvp-scope-and-gap-map.md`;
- `04-data-and-api-contracts.md`, раздел о состояниях;
- текущие `contracts.ts`, `tsconfig.json` и настройки сборки.

**Входит:**

- общий модуль со Zod-схемой `generic | materials_rnd`;
- TypeScript-тип, выведенный из этой схемы;
- функция разбора с default `generic` только для отсутствующего значения;
- unit-тесты допустимых значений, неизвестного значения и отсутствующего поля.

**Не входит:**

- передача profile через IPC, WorkerData или renderer;
- отдельный materials engine;
- UI preview;
- агенты;
- RAG;
- изменения generic planner.

**Критерии:**

1. `generic` и `materials_rnd` проходят схему;
2. отсутствующее значение нормализуется в `generic`;
3. неизвестное значение возвращает структурированную ошибку parse;
4. runtime приложения ещё не меняет поведения;
5. новые тесты и build проходят.

**Остановка:** если общий модуль нельзя безопасно импортировать main и renderer без изменения конфигурации сборки, Codex останавливается и описывает минимальные варианты размещения; он не дублирует схему молча.

## 9. Формат запроса к Codex

```text
Выполни карточку M0.1 из docs/materials-orchestrator/09-codex-execution-playbook.md.

Сначала проверь её зависимости и текущее состояние указанных файлов. Не переходи к M0.2.
Сохрани generic-поведение. Выполни все проверки из карточки и в конце перечисли:
1) изменённые файлы;
2) результаты тестов и сборки;
3) ограничения или отклонения от ТЗ;
4) готова ли карточка к статусу review.
```

После создания отдельных файлов task cards этот запрос должен ссылаться на конкретный файл, а не на раздел playbook.

Первая отдельная карточка уже подготовлена: [tasks/M0.1-workflow-profile.md](./tasks/M0.1-workflow-profile.md).

## 10. Что проверяет ревьюер

- задача действительно одна;
- не расширен scope;
- новый payload валидируется;
- негативный тест не фиктивен;
- generic regression существует;
- ошибки и fallback видимы;
- нет скрытого сетевого обращения;
- нет hardcoded success/confidence;
- документация соответствует коду;
- результат можно безопасно откатить обычным git revert задачи.

## 12. Обновление документации и Obsidian

Код и нормативные документы сначала изменяются в репозитории. После проверки документы копируются в Obsidian и сверяются по SHA-256. Код, fixtures и тесты в Obsidian не дублируются.

Ручная правка обеих копий одного документа запрещена: она создаёт незаметное расхождение.

## 13. Когда требуется решение владельца

Codex останавливается, если задача требует:

- платной лицензии или нового аккаунта;
- изменения границы физического контроля;
- нового внешнего сервиса по умолчанию;
- несовместимой миграции без безопасного пути;
- замены TypeScript runtime;
- научной модели без лицензии или ModelCard;
- удаления пользовательских данных;
- решения, которое существенно меняет scope MVP.

## 14. Что означает «пакет готов к Codex»

Пакет готов, когда существуют:

- утверждённая архитектура;
- границы MVP и карта пробелов;
- нормативные контракты;
- AgentSpec и ToolSpec;
- backlog с зависимостями;
- тестовая стратегия;
- golden scenario;
- task card для первого шага;
- правила ведения статусов и отчётов.

После этого можно активировать корневые инструкции для Codex и запускать карточку `M0.1`. До этого момента настоящий код материаловедческого профиля не изменяется.
