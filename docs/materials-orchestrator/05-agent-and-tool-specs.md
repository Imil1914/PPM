# AntyFlow Materials R&D: агенты, инструменты и жизненный цикл

**Статус:** нормативное ТЗ  
**Главное правило:** агент рассуждает и выбирает следующий допустимый шаг; инструмент выполняет узкую проверяемую операцию

## 1. Что называется агентом

В AntyFlow агент состоит из пяти частей:

1. зарегистрированная роль `AgentSpec`;
2. выбранная модель;
3. конкретная задача из графа;
4. минимальный `ContextBundle`;
5. временная аренда разрешённых инструментов.

Модель без этих ограничений является просто LLM-вызовом. `AgentSpec` без запуска является шаблоном роли. Живой временный экземпляр называется `AgentRun`.

Агент не равен научной модели. Он может решить, когда запросить фазовый расчёт, но не должен изображать CALPHAD-расчёт собственным текстом.

## 2. Как создаётся динамический агент

```text
готовый узел графа
  → CapabilityRequest
  → поиск подходящих AgentSpec
  → фильтр прав и бюджета
  → выбор модели
  → AgentRun
  → ContextBundle
  → временные ToolLease
  → выполнение
  → проверка AgentResult
  → сохранение результата
  → отзыв прав и завершение
```

Другой агент может предложить новую подзадачу через `ChangeRequest`, но не может создать экземпляр агента или изменить граф самостоятельно.

## 3. Состояния `AgentRun`

| Состояние | Смысл |
|---|---|
| `requested` | Граф запросил способность |
| `selected` | Оркестратор выбрал AgentSpec и модель |
| `leased` | Выданы временный контекст и инструменты |
| `running` | Агент рассуждает или готовит вызов инструмента |
| `waiting_tool` | Агент ожидает контролируемый ToolGateway |
| `submitted` | Агент закончил и передал результат |
| `validating` | Результат проходит контрактные и доменные проверки |
| `completed` | Проверенный результат сохранён |
| `failed` | Результат не получен или не прошёл допустимое исправление |
| `cancelled` | Запуск остановлен политикой или человеком |
| `expired` | Истёк TTL или heartbeat |

Любое терминальное состояние отзывает аренды. История, трасса и уже сохранённые версии остаются.

## 4. Целевой каталог ролей

Каталог содержит роли, а не постоянно работающие процессы. Для сложного проекта может быть зарегистрировано 14 ролей, но одновременно активируются только необходимые, обычно 3–6.

### `AG-REQ` — агент требований

- Превращает черновой запрос в список проверяемых требований.
- Находит отсутствующие и противоречивые поля.
- Предлагает компактную группу вопросов.
- Может записывать только предложения к `ResearchGoal`.
- Не выбирает состав и не утверждает допущение вместо инженера.

### `AG-ARCH` — архитектор исследования

- Создаёт `PlanDraft` по утверждённой версии цели.
- Определяет зависимости и параллельные ветви.
- Запрашивает способности, а не конкретные процессы.
- Не формирует исполняемый граф напрямую.

### `AG-EVID` — агент литературы и доказательств

- Формирует запросы к Knowledge Router.
- Ищет источники и подтверждающие фрагменты.
- Сохраняет противоречащие позиции отдельно.
- Не публикует утверждение без Evidence Commit Gate.

### `AG-DATA` — куратор численных данных

- Извлекает составы, условия, свойства, единицы и таблицы.
- Привязывает каждое значение к `SourceSpan`.
- Обнаруживает несопоставимые условия.
- Не исправляет неизвестную единицу догадкой.

### `AG-COMP` — проектировщик состава

- Создаёт несколько семейств гипотез состава.
- Учитывает ограничения и известные механизмы упрочнения.
- Может применять ТРИЗ для генерации альтернатив.
- Не объявляет гипотезу готовой рецептурой.

### `AG-ROUTE` — проектировщик маршрутов

- Создаёт маршруты для конкретной версии состава.
- Сравнивает литьё с деформацией, прокат, ковку, порошковую металлургию и аддитивное изготовление, если они разрешены.
- Вызывает проверку технологической выполнимости.
- Не скрывает причину исключения маршрута.

### `AG-PHASE` — интерпретатор фазовых расчётов

- Подготавливает корректный вход строгому фазовому инструменту.
- Интерпретирует выход в пределах области применимости.
- Фиксирует риск нежелательных фаз.
- Не генерирует числа при недоступном solver.

### `AG-MICRO` — агент микроструктуры и дефектов

- Связывает маршрут с гипотезой структуры и дефектов.
- Вызывает зарегистрированные модели или правила.
- Разделяет наблюдение, модельный прогноз и гипотезу.

### `AG-PROP` — агент прогнозирования свойств

- Выбирает подходящую зарегистрированную модель по ModelCard.
- Проверяет область применимости.
- Возвращает прогноз только вместе с условиями и неопределённостью.

### `AG-UQ` — агент неопределённости

- Собирает информационную, модельную и экспериментальную неопределённость.
- Находит кандидаты с недостатком данных.
- Не подменяет UQ произвольным значением confidence LLM.

### `AG-DOE` — планировщик экспериментов

- Выбирает минимальный информативный набор будущих опытов.
- Учитывает стоимость и ожидаемое уменьшение неопределённости.
- Не запускает физический эксперимент.

### `AG-CRIT` — независимый научный критик

- Проверяет пакет на причинные скачки, слабое происхождение, несовместимые условия и выход модели за domain.
- Возвращает адресные `ChangeRequest`.
- Использует отдельный AgentRun; для критических решений предпочтительны другая сессия и при возможности другая модель.
- Не может сам пометить пакет утверждённым.

### `AG-PUB` — технический редактор и сборщик представлений

- Превращает утверждённую структуру пакета в понятные представления.
- Не изменяет научные значения при форматировании.
- Не создаёт отдельную «истину» для презентации.

### `AG-KNOW` — куратор знаний

- Проверяет предложения в граф знаний.
- Управляет конфликтами, версиями и статусами claims.
- Инициирует инвалидацию зависимых объектов.
- Не удаляет неудобное противоречащее свидетельство.

## 5. Группировка ролей для первой версии

Чтобы не создавать избыточный «базар агентов», первые рабочие AgentSpec могут объединять соседние функции:

| MVP AgentSpec | Объединённые роли |
|---|---|
| `requirements_architect` | `AG-REQ`, `AG-ARCH` |
| `evidence_data_curator` | `AG-EVID`, `AG-DATA` |
| `composition_route_designer` | `AG-COMP`, `AG-ROUTE` |
| `science_interpreter` | `AG-PHASE`, `AG-MICRO`, `AG-PROP`, но только через строгие инструменты |
| `optimization_planner` | `AG-UQ`, `AG-DOE` и интерпретация Pareto |
| `independent_critic` | `AG-CRIT`, техническая проверка пакета |

`AG-PUB` и `AG-KNOW` в MVP могут быть детерминированными узлами. Разделение одной объединённой роли выполняется только тогда, когда её контекст, инструменты или критерии качества стали конфликтовать.

## 6. Нормативный шаблон `AgentSpec`

Каждый файл спецификации роли обязан содержать:

```yaml
id: evidence_data_curator
version: 1
name: Куратор доказательств и данных
purpose: Найти и структурировать доказательства для конкретных вопросов графа.

created_when:
  required_capability: evidence_retrieval

allowed_goals:
  - искать источники
  - извлекать фрагменты и численные записи
  - регистрировать противоречия

forbidden_actions:
  - менять ResearchGoal
  - менять исполняемый граф
  - публиковать неподтверждённый claim
  - утверждать экспериментальный пакет

input_contracts:
  - EvidenceRequestV1
  - ContextBundleV1

output_contracts:
  - AgentResultV1<EvidenceBundleV1>

allowed_tools:
  - source_search
  - source_span_reader
  - hybrid_retrieve
  - structured_materials_query
  - unit_normalizer

context_policy:
  maximum_context_tokens: 24000
  include_only:
    - текущая цель
    - конкретный вопрос
    - связанные решения

model_policy:
  preferred_tier: standard
  escalate_when:
    - источники противоречат друг другу
    - требуется multi-hop интерпретация

limits:
  ttl_ms: 300000
  maximum_attempts: 3
  maximum_tool_calls: 20
  maximum_tokens: 24000

success_rules:
  - каждый факт имеет SourceSpan
  - единицы и условия заполнены
  - противоречия не скрыты
```

## 7. Выбор модели

Модель выбирается не по названию роли, а по риску конкретного узла.

### Локальная или недорогая модель, например Qwen

Подходит для:

- классификации и маршрутизации;
- извлечения структурированных полей;
- нормализации текста;
- построения поисковых запросов;
- форматирования уже проверенных данных;
- первичного черновика при строгом контракте.

### Стандартная модель

Подходит для:

- сравнения источников;
- проектирования маршрутов по предоставленным данным;
- интерпретации проверенных результатов инструментов;
- формирования пояснений к кандидатам.

### Сильная модель

Используется для:

- первоначальной архитектуры сложного исследования;
- противоречивой доказательной базы;
- критической научной критики;
- локального перепланирования высокорисковой ветви;
- финального синтеза перед Human Gate 2.

Эскалация должна иметь записанную причину. Сильная модель не освобождается от контрактов и проверок.

## 9. Нормативный шаблон `ToolSpec`

```yaml
id: property_predictor
version: 1
name: Прогноз свойств
kind: sidecar
purpose: Получить прогноз одного свойства для версии CandidateDesign.

input_contract: PropertyPredictionRequestV1
output_contract: PropertyPredictionV1

preconditions:
  - состав нормализован
  - маршрут имеет версию
  - условия испытания заданы

side_effects:
  - none

permissions:
  network: false
  filesystem_read: false
  filesystem_write: false

timeout_ms: 120000
maximum_retries: 1
idempotent: true

failure_codes:
  - model_unavailable
  - outside_training_domain
  - unsupported_composition
  - invalid_units

provenance_fields:
  - model_id
  - model_version
  - input_snapshot
  - applicability
  - execution_time
```

Инструмент, которого нет в реестре, вызвать невозможно. Тестовый адаптер обязан иметь `implementation_kind: fixture` и не может отображаться пользователю как реальный научный расчёт.

## 11. Ограничение контекста

Агент получает только:

- цель и конкретный узел;
- версии входных объектов;
- найденные доказательства по вопросу;
- необходимые прошлые решения;
- список допустимых инструментов;
- критерии успеха и бюджет.

Агент не получает автоматически все PDF, весь журнал, выводы всех ветвей и ключи провайдеров. Это уменьшает шум, стоимость и утечки контекста.

## 12. Проверка результата агента

Результат проходит четыре уровня:

1. контрактная форма;
2. права и использованные инструменты;
3. доменные правила и единицы;
4. происхождение claims.

Ошибка формы может повторить тот же узел. Научная проблема создаёт адресный feedback. Недостаток полномочий эскалируется. После исчерпания попыток результат не превращается автоматически в success.

## 13. Независимость критика

Для `AG-CRIT` запрещено:

- использовать тот же `AgentRun`, который создавал решение;
- читать скрытые chain-of-thought или внутренние черновики автора;
- менять проверяемый результат во время оценки;
- утверждать пакет.

Критик получает утверждённые входы, проверяемый пакет, критерии и ссылки на доказательства. Его выход — `CritiqueReport` и адресные `ChangeRequest`.

## 14. Создание, остановка и уничтожение

### Нормальное завершение

1. Агент отправляет `AgentResult`.
2. Оркестратор переводит run в `validating`.
3. После проверки результат получает версию.
4. ToolLease отзываются.
5. Временный контекст удаляется по политике.
6. AgentRun получает `completed`.

### Отмена

1. Новые вызовы инструментов запрещаются.
2. Агенту отправляется мягкая остановка.
3. Сохраняется checkpoint, если он валиден.
4. После grace period выполнение принудительно завершается.
5. AgentRun получает `cancelled`.

### TTL или зависание

После пропуска heartbeat или TTL ToolLease отзываются немедленно. Feedback Hub решает, повторить узел, выбрать другой AgentSpec или эскалировать человеку.

## 15. Критерий готовности агентного слоя

Слой готов, если capability-запрос выбирает только разрешённую роль, каждый инструмент проходит ToolGateway, AgentRun имеет наблюдаемый жизненный цикл, права отзываются во всех терминальных состояниях, ошибки не превращаются в успех, а агент не может напрямую изменить граф или создать другого агента.
