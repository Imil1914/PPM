# Цель

Создать детерминированную внешнюю JSON Schema-проекцию всех принятых V1-контрактов M1.1. Каждый документ генерируется только из нормативного Zod-объекта встроенным API Zod 4; ручное повторение полей, типов и enum запрещено.

# Зависимость

M1.1 принята владельцем. В barrel `materials/contracts/index.ts` находится ровно 44 публичных объекта `*V1Schema`; полный baseline после M1.1 — 17 test-файлов и 410/410 тестов.

# Канонический источник и версия генератора

- Нормативный валидатор: Zod-схема M1.1.
- Установленный генератор: встроенный `z.toJSONSchema` из Zod `4.4.3`.
- Dialect: `draft-2020-12`.
- Режим: `io: 'input'`, потому что описывается недоверенный входной payload.
- Непредставимый тип: `unrepresentable: 'throw'`, без тихой подмены на `{}`.
- Текущие схемы ацикличны: `cycles: 'throw'` должен остановить неожиданную рекурсию.
- Повторно используемые вложения: `reused: 'inline'`, чтобы каждая схема была автономной и не зависела от нестабильного `__shared`.

# Входит в задачу

1. Создать типизированный реестр всех 44 публичных `*V1Schema`, ключуемый точным именем контракта без суффикса `Schema`, например `ResearchGoalV1`.
2. Добавить публичные функции:
   - получить нормативную Zod-схему по имени;
   - сгенерировать автономную JSON Schema одного контракта;
   - сгенерировать полный отсортированный каталог `name → JSON Schema`;
   - канонически сериализовать каталог с рекурсивно отсортированными object keys и неизменным порядком массивов.
3. Каждый результат содержит точный `$schema: https://json-schema.org/draft/2020-12/schema` и является обычным JSON после stringify/parse.
4. Добавить автоматическую полноту реестра:
   - множества публичных `*V1Schema`, Zod-реестра и JSON-каталога совпадают;
   - factory `createAgentResultV1Schema` не является отдельной записью;
   - schema instance в реестре идентичен публичному export.
5. Переиспользовать 44 test cases M1.1 через отдельный test-only fixture registry, не копируя второй раз full/minimal fixtures.
6. Для каждой схемы проверить JSON Schema round-trip в пределах представимой структуры.
7. Создать полный стабильный Vitest file snapshot канонического каталога. Snapshot является автоматически сгенерированным артефактом, а не вторым вручную поддерживаемым контрактом.
8. Явно протестировать и документировать границу custom refinements: внешняя JSON Schema не заменяет повторную Zod-валидацию в main.

# Точное определение round-trip M1.2

Для каждого из 44 контрактов:

```text
normative Zod
  → z.toJSONSchema Draft 2020-12
  → JSON.stringify
  → JSON.parse
  → z.fromJSONSchema (только тестовый structural validator)
  → full/minimal fixtures и structural negatives
```

Обязательные проверки:

- full и minimal fixtures принимаются исходной Zod-схемой и round-trip validator;
- удаление каждого обязательного корневого поля отклоняется;
- неверный JSON-тип типизированного обязательного корневого поля отклоняется;
- лишнее корневое поле отклоняется через `additionalProperties: false`;
- представимые enum, literal, pattern, required, numeric/string/array bounds сохраняются;
- два последовательных вызова дают побайтово одинаковую каноническую сериализацию.

`z.fromJSONSchema` используется только в тестах. Production API возвращает JSON Schema, а окончательный gate остаётся исходной Zod-схемой.

# Ограничение custom refinements

Zod 4.4.3 не переносит `.refine()` и `.superRefine()` в JSON Schema и не сообщает об этом как об `unrepresentable` type. Поэтому JSON Schema является структурной обменной проекцией, но не полной заменой Zod. В частности, только Zod продолжает проверять:

- внешние пробелы обязательных строк;
- непустой locator и порядок char offsets;
- наличие и порядок границ interval;
- положительную сумму весов и пересечение required/forbidden elements;
- provenance у `reported_fact`;
- исключительность `side_effects: ['none']`;
- change requests для `request_changes`;
- approval decision у утверждённого package.

Ручное дописывание этих правил в JSON Schema в M1.2 запрещено: оно создаст второй источник истины.

# Не входит в задачу

- изменение shapes, optional/required полей, enum или refinements M1.1;
- миграции V0/V1 и SQLite — M1.3;
- `VersionRef` resolution и repository — M1.4;
- main/IPC/preload/renderer wiring и bypass tests;
- Pydantic/Python code generation;
- Ajv или новая dependency;
- remote publication, канонический HTTP/URN `$id`, filenames и API endpoint;
- статические вручную написанные `.schema.json`;
- специализированные JSON Schema для каждого concrete `AgentResultV1<TOutput>`;
- graph compiler, agent runtime, RAG и доменные научные правила;
- изменение M0.6 baseline manifest.

# Критерии приёмки

1. Реестр содержит ровно 44 принятые V1-схемы без пропусков, лишних записей или дублей.
2. Все JSON Schema генерируются из реальных Zod instances с фиксированными параметрами и target Draft 2020-12.
3. Нет ручного повторения domain shapes или TypeScript interfaces.
4. Все документы автономны, JSON-serializable, не содержат `__shared`, `__schemaN`, `definitions` или служебного enumerable `~standard`.
5. Full/minimal fixtures и представимые structural negatives проходят round-trip для всех 44 схем.
6. Строгость объектов, required fields, schema literal, enum и представимые диапазоны сохраняются.
7. Полный канонический каталог детерминирован и совпадает с committed snapshot.
8. Отдельный тест показывает, что custom refinement остаётся Zod-only; документация запрещает считать JSON Schema окончательным scientific/runtime gate.
9. `npm test`, `npm run build` и baseline guard проходят; новых TypeScript fingerprints нет.
10. Generic regression проходит, production не импортирует JSON Schema-модуль до отдельной integration card.
11. Документы репозитория и Obsidian совпадают по относительным путям и SHA-256.

# Правила остановки

Остановиться и запросить решение владельца, если:

- хотя бы одна принятая V1-схема не представима при `unrepresentable: 'throw'`;
- для стабильного экспорта требуется менять shape или dependency;
- round-trip не может сохранить обязательную структурную проверку, которую Zod выражает без custom refine;
- snapshot нестабилен между двумя последовательными запусками без изменения входов;
- появляется новая TypeScript-диагностика;
- задача расширяется до M1.3 или production wiring.

# Итог реализации

- Создан публичный типизированный реестр ровно из 44 нормативных Zod-схем V1 и API получения исходной схемы, генерации одного JSON Schema, полного каталога и его канонической сериализации.
- Все документы автономно генерируются встроенным `z.toJSONSchema` Zod 4.4.3 с зафиксированными параметрами `draft-2020-12`, `io: input`, `unrepresentable: throw`, `cycles: throw`, `reused: inline`; ручных копий domain shapes нет.
- Полнота доказана сравнением реестра с публичными экспортами и единой матрицей 44 fixtures. Factory `createAgentResultV1Schema` не попал в реестр, а каждая запись сохраняет identity исходного Zod instance.
- Structural round-trip проверяет full/minimal fixtures, каждое обязательное корневое поле, неверные JSON-типы и лишние поля для всех 44 контрактов. Отдельный тест показывает, что custom refinement `reported_fact → evidence` остаётся только в нормативном Zod-gate.
- Канонизация рекурсивно сортирует object keys, сохраняет специальные JSON-ключи вроде `__proto__` и fail-closed отклоняет циклы, `NaN`, `Infinity`, `undefined`, функции, symbol keys и непростые объекты вместо тихой потери данных.
- Полный generated snapshot имеет размер 173380 байт и стабильный SHA-256 `34F8AAA1EC294160CD4B1C6DD92410C140AF37330EE8C82EC27FE3B6095B7DA0` между повторными запусками.
- Финальные проверки: JSON Schema 185/185, весь contract suite 500/500, baseline guard 3/3, весь проект 18 test-файлов и 595/595 тестов; production build прошёл, новых TypeScript fingerprints нет.
- Два независимых read-only ревью не нашли блокирующих замечаний. Два замечания по fail-closed канонизации были устранены до финального прогона.
- JSON Schema-модуль не импортируется production-кодом за пределами `materials/contracts`; IPC, engine, DB и M1.3 не затронуты. Карточка готова к приёмке владельцем; M1.3 автоматически не запускается.
