# Цель

Создать единый test-only `FakeRuntime`, через который движок, режимы и будущий материаловедческий граф можно проверять без Electron, worker_threads, сети, LLM, внешних баз знаний и пользовательских данных.

FakeRuntime должен быть детерминированным, изолированным между тестами и завершаться явной ошибкой при незаданном внешнем эффекте.

# Зачем это нужно

Сейчас каждый интеграционный тест вручную собирает неполный объект `Runtime` через `as unknown as Runtime`. Такие объекты скрывают отсутствующие методы, по-разному моделируют Vault и позволяют случайному сетевому вызову остаться незамеченным. До появления материаловедческих контрактов, агентов и инструментов нужен один проверяемый стенд.

# Входит в задачу

1. Создать `src/main/orchestrator/__tests__/fakeRuntime.ts` с классом, полностью реализующим текущий интерфейс `Runtime`.
2. Не импортировать Electron, worker_threads, файловую систему, сеть или тестовые mock-библиотеки в FakeRuntime.
3. Реализовать изолированный in-memory Vault:
   - write/read/readMany;
   - metadata;
   - append-only task logs.
   `vaultQuery` считать границей будущего retrieval-слоя и задавать только явным fixture, не копируя в тест семантику будущего RAG.
4. Сохранять trace, status, board nodes и аргументы всех runtime-вызовов для проверок.
5. Генерировать ID детерминированными счётчиками отдельно по project и prefix. Экземпляры одного project могут разделять test-only backend; разные project изолированы.
6. Управлять отменой явным методом теста.
7. Не копировать production-поиск кандидатов: `findCandidates` задавать явным fixture/resolver с известным порядком узлов.
8. Для внешних эффектов использовать строгие очереди fixtures с опциональным matcher аргументов:
   - `aiChat`;
   - `vaultQuery`;
   - `findCandidates`;
   - `humanRequest`;
   - `spawnSub`;
   - `papersSearch` и `papersPdf`;
   - `anythingEnsure` и `anythingIngest`;
   - `boardCreateNodes`;
   - `webLLMAsk`.
9. Пустая очередь внешнего эффекта обязана бросать понятную ошибку; скрытый success/fallback запрещён.
10. Очередь может содержать успешный ответ, отрицательный ответ или объект `Error`, который пробрасывается тем же экземпляром.
    Неожиданный вызов остаётся в sticky-журнале, поэтому финальная проверка падает, даже если production-код перехватил исходную ошибку.
11. Вести наблюдаемый ledger фактически потреблённых model fixtures (tokens/calls). Не копировать политику `BudgetManager`: ответ `budget_exceeded` и отмену задавать явно, а чистую production-логику budget тестировать напрямую.
12. Добавить test-only builders типизированных model, node, paper и TaskResult fixtures.
13. Добавить self-tests FakeRuntime.
14. Добавить минимум один интеграционный тест реального engine через FakeRuntime:
    - DAG с зависимостями;
    - Vault retrieval между узлами;
    - model usage ledger;
    - human decision.

# Не входит в задачу

- изменения production-кода и интерфейса `Runtime`;
- временная SQLite или миграции;
- Fake Worker, IPC или renderer;
- полноценные fixtures алюминиевой пластины до появления Zod-контрактов;
- эмуляция реального планировщика времени, параллелизма потоков или сети;
- научные ToolSpec и настоящие адаптеры;
- изменение BudgetManager;
- snapshot полного текста prompts;
- исправление сторонних TypeScript-ошибок;
- сборка установщика.

# Разрешённые файлы

- новый `src/main/orchestrator/__tests__/fakeRuntime.ts`;
- новый `src/main/orchestrator/__tests__/fakeFixtures.ts`;
- новые `fakeRuntime*.test.ts` в той же папке;
- существующие orchestrator tests — только если перенос на FakeRuntime очевидно сокращает ручной stub;
- документы статусов, README и changelog.

Production-файлы, контракты, engine, profiles, worker, IPC, renderer, БД и конфигурация сборки не изменяются.

# Инварианты

## Изоляция

```text
два независимых backend или два разных project → Vault изолирован
root и child одного project на общем backend → разделяют Vault/cancel/ID
```

## Внешний эффект

```text
нет подходящего queued fixture
→ вызов бросает UnexpectedFakeRuntimeCall
→ сеть и реальный сервис не вызываются
```

## Очередь и matcher

```text
queued [response A, Error B, response C]
→ вызовы получают A, затем тот же Error B, затем C

при параллельных вызовах matcher выбирает подходящий fixture
→ порядок завершения Promise не меняет назначение ответа
```

## Budget boundary

```text
успешный queued ai response → ledger учитывает tokens/call
budget_exceeded → явный scripted response
production BudgetManager → проверяется отдельно без дублирования внутри FakeRuntime
```

## Engine

Реальный engine получает объект, который структурно является `Runtime`, и не знает, что работает в тесте. Результат возникает только из явно заданных fixtures и in-memory данных.

# Критерии приёмки

1. `FakeRuntime implements Runtime` без `as unknown` внутри реализации.
2. Все методы Runtime реализованы и журналируют вызовы.
3. Ни один метод FakeRuntime не обращается к сети, диску, Electron или LLM.
4. Vault операции, metadata и task logs детерминированы; retrieval задаётся явно.
5. Одинаковый project на общем backend разделяет Vault/cancel/ID, разные project изолированы.
6. ID и cancellation управляемы и повторяемы.
7. Candidate response задаётся явно; FakeRuntime не дублирует production ranking.
8. Все внешние очереди поддерживают matcher и fail-fast при отсутствии подходящего fixture.
9. Error fixture пробрасывается по identity.
10. Model usage ledger совпадает с суммой фактически завершённых model fixtures.
11. `budget_exceeded` и отмена воспроизводятся scripted response без копии BudgetManager.
12. Board/tool/retrieval/human/sub-orchestrator вызовы доступны без внешних сервисов и наблюдаемы тестом.
13. Реальный engine выполняет минимум двухузловой DAG через FakeRuntime.
14. Зависимый узел получает вывод предшественника через Vault.
15. Human decision fixture меняет только ожидающую ветвь по существующей логике engine.
16. Fixtures явно находятся в `__tests__` и не регистрируются как реальные адаптеры.
17. Production diff M0.5 пуст.
18. `npm test` и `npm run build` проходят.
19. Новых TypeScript-ошибок нет.

# Отчёт о выполнении — 2026-08-28

Карточка реализована, технически проверена и принята владельцем перед началом M0.6.

## Возможности FakeRuntime

- `FakeRuntime implements Runtime` напрямую и реализует весь текущий контракт без неполных `as unknown as Runtime`-заглушек.
- In-memory Vault поддерживает write/read/readMany, metadata, task logs и защитные копии данных.
- Общий `FakeRuntimeBackend` позволяет root и child одного project разделять Vault, отмену и ID; разные project изолированы.
- ID формируются детерминированно отдельными счётчиками по project и prefix; время и случайность не используются.
- Trace, status, board nodes, model usage и аргументы всех Runtime-вызовов доступны тестам.
- Внешние эффекты задаются строгими очередями с matcher; подходящий fixture изымается синхронно при входе в вызов.
- Неожиданные вызовы сохраняются в sticky-журнале, а `verify()` обнаруживает как их, так и неиспользованные fixtures.
- Возвращаемые данные клонируются; scripted `Error` пробрасывается тем же экземпляром.
- `findCandidates` и `vaultQuery` не копируют production ranking или будущую RAG-семантику: их ответы задаются явно.

## Граница внешних эффектов

| Runtime-вызов | Поведение FakeRuntime | Без fixture |
|---|---|---|
| `vaultWrite/read/readMany`, `vaultAppendLog` | Безопасный in-memory backend | Выполняется локально |
| `trace`, `status`, `isCancelled`, `newId` | Детерминированное состояние и журналы | Выполняется локально |
| `aiChat` | Scripted response/Error + usage ledger | `UnexpectedFakeRuntimeCall` |
| `vaultQuery`, `findCandidates` | Только явный response/matcher | `UnexpectedFakeRuntimeCall` |
| `humanRequest`, `spawnSub` | Только явное решение/результат | `UnexpectedFakeRuntimeCall` |
| `papersSearch`, `papersPdf` | Только синтетические fixtures | `UnexpectedFakeRuntimeCall` |
| `anythingEnsure`, `anythingIngest` | Только scripted boundary | `UnexpectedFakeRuntimeCall` |
| `boardCreateNodes`, `webLLMAsk` | Только scripted boundary; вызовы журналируются | `UnexpectedFakeRuntimeCall` |

Ни один путь FakeRuntime не импортирует Electron, worker_threads, файловую систему, сеть, LLM SDK или test mock library.

## Реальные интеграционные сценарии engine

1. Production router запускает `materials_rnd` при `depth = 1` и выполняет DAG `t1 → t2` без module mocks.
2. Вывод `t1` записывается в Vault, загружается реальным mode-кодом и присутствует в user prompt узла `t2`.
3. Два одинаковых запуска дают одинаковые TaskResult, Vault, вызовы, ID и канонический trace без полей production-времени.
4. Actor–Critic с одной итерацией и низкой оценкой эскалирует только ветвь `review` инженеру; scripted `approve` переводит её в success, пока независимая sibling pipeline-ветвь также успешно завершается.
5. Отдельный self-test воспроизводит `budget_exceeded`, usage ledger и отмену без повторной реализации production `BudgetManager`.

## Ограничение

`FakeRuntime моделирует текущий Runtime и не является научным симулятором, Fake Worker или заменой будущих Zod-fixtures.`

Queued fixtures считаются неизменяемыми после регистрации, а matcher/resolver — чистыми функциями: test runtime хранит fixture по ссылке до потребления и не пытается клонировать функции или `Error`.
