# Цель

Продолжить единый журнал миграций `flow.db` версией 4 и создать минимальный физический фундамент для будущего `VersionRepository` M1.4. Миграция должна одинаково безопасно применяться к новой и существующей базе, сохранять legacy-данные и откатывать незавершённый `up` целиком.

# Разрешение неоднозначности M1.2

M1.3 мигрирует схему SQLite, а не доменные payload `V0 → V1`.

- В проекте нет ни одной нормативной `*V0Schema` и нет сохранённых материаловедческих V0-объектов.
- Строка `goal_aluminium_plate_v0` в fixture является идентификатором предыдущего объекта, а не именем контракта.
- Изобретать V0-shapes или угадывать тип payload по набору полей запрещено.
- Payload migration registry появится только вместе с первым реальным V2 и его нормативной исходной схемой.

Нужно различать три независимых понятия:

```text
schema_migrations.version = 4  — версия физической схемы SQLite
contract_id = ResearchGoalV1   — точный внешний ключ Zod-контракта
entity_revision = 1, 2, ...    — версия конкретного предметного объекта
```

# Состояние до начала

- `src/main/db.ts` содержит глобальные миграции 1–3 и журнал `schema_migrations`.
- Миграции выполняются по одной транзакции, но runner приватен и не тестируется реальной SQLite.
- Любая ошибка `openFresh`, включая ошибку кода миграции, сейчас может попасть в recovery повреждённой БД. Для ошибки миграции это недопустимо: исправный пользовательский файл нельзя переименовывать и заменять пустым.
- `better-sqlite3` уже является production dependency, но локальный console Node 24 не имеет собранного native binding. Test-only `node:sqlite` доступен и исполняет настоящий SQLite 3.50.3; он проверяет общий SQL и транзакции, но не Electron ABI.

# Физическая модель v4

## `materials_projects`

Минимальные поля:

- `project_id` — primary key;
- `board_id` — связь с доской Flow;
- `workflow_profile` — только `materials_rnd`;
- `status` — строковое состояние, окончательно валидируемое Zod;
- `created_at`, `updated_at` — ISO UTC на runtime-границе;
- `created_by_kind`, `created_by_id` — actor envelope;
- индекс по `board_id`.

SQL не копирует enum статусов целиком: Zod остаётся нормативным источником.

## `materials_object_versions`

Канонический append-only envelope:

- `record_id` — неизменяемый идентификатор физической записи;
- `project_id` — внешний ключ на `materials_projects` с `RESTRICT`;
- `contract_id` — точный внешний ключ контракта, например `ResearchGoalV1`;
- `entity_id` и положительный `entity_revision` — адрес `VersionRef` внутри проекта;
- `payload_json` — валидный JSON object;
- `payload_sha256` — 64 lowercase hex символа;
- `supersedes_record_id` — nullable точная ссылка на предыдущую запись того же проекта;
- `created_at`, `created_by_kind`, `created_by_id`;
- уникальность `(project_id, contract_id, entity_id, entity_revision)`;
- индексы истории, predecessor и hash;
- запрет `UPDATE` и `DELETE` триггерами.

Список 44 contract ids не дублируется в SQL CHECK. Проверка известного `contract_id`, совпадения внутреннего `schema_version`, Zod parse и семантики supersede относится к M1.4.

# Migration runner

1. Существующие миграции 1–3 переносятся без изменения SQL в чистый модуль.
2. Полный manifest содержит уникальную непрерывную последовательность `1..4`.
3. Пропуск применённой версии или неизвестная более новая версия БД отклоняются fail-closed.
4. Каждая ещё не применённая миграция выполняется через `BEGIN IMMEDIATE`.
5. Тело `up` и запись в `schema_migrations` входят в одну транзакцию.
6. При ошибке выполняется `ROLLBACK`; частичной схемы и marker версии не остаётся.
7. Ошибка имеет отдельный тип `DatabaseMigrationError` и сохраняет исходную причину.
8. `getDb` не трактует `DatabaseMigrationError` как физическую порчу, не переносит исходный файл и не создаёт пустую замену.
9. Повторный запуск идемпотентен и не меняет `applied_at`.
10. Production выполняет только `up`; downgrade пользовательской базы отсутствует.

# Точное толкование rollback

Rollback M1.3 — это атомарный откат неуспешного `up`. Rehearsal выполняется на физической временной копии закрытого SQLite-файла:

1. создаётся база уровня 3 с legacy-строкой;
2. файл копируется;
3. к копии добавляется тестовая падающая миграция;
4. проверяется отсутствие её таблиц, строк и migration marker;
5. исходный файл повторно открывается и имеет прежний SHA-256 и данные.

Production down-migration не создаётся и над пользовательской `flow.db` не запускается.

# Входит в задачу

- общий тестируемый migration runner;
- сохранение SQL и поведения миграций 1–3;
- глобальная миграция 4 с двумя фундаментальными materials-таблицами;
- минимальное подключение нового manifest в `db.ts`;
- безопасная классификация migration failure;
- реальные SQLite-тесты через test-only `node:sqlite`;
- fresh, existing-v3, idempotence, constraints, history, future-version и rollback-copy tests;
- полный regression, build, baseline и документация.

- выдуманные V0-контракты и payload migration registry;
- CRUD `VersionRepository`, разрешение `VersionRef` и supersede-команды — M1.4;
- append-only `project_events` и replay — M1.5;

- автоматический rebuild `better-sqlite3` под console Node, способный нарушить Electron ABI;

# Критерии приёмки

1. Свежая БД получает migration markers `1, 2, 3, 4`, обе v4-таблицы, индексы, FK и append-only triggers.
2. Физическая копия существующей БД уровня 3 получает только версию 4; legacy-таблицы и контрольные строки сохраняются.
3. Второй запуск не применяет миграции повторно и не меняет их `applied_at`.
4. Manifest с duplicate/gap, история с gap и БД с неизвестной future version отклоняются до domain writes.
5. Невалидный JSON-object, revision 0, duplicate VersionRef, неизвестный проект, broken/cross-project predecessor и неверный hash отклоняются SQLite.
6. `UPDATE` и `DELETE` version row запрещены.
7. Падающая миграция на временной копии не оставляет DDL, DML или marker; оригинал не меняется.
8. Migration failure не проходит через recovery физически повреждённой БД.
9. Миграции 1–3 остаются структурно и функционально прежними; generic-пути не получают нового поведения.
10. Общий SQL исполняется настоящей SQLite в tests; production adapter проходит TypeScript/build. Ограничение отсутствующего локального native ABI явно остаётся ручным Electron smoke gate.
11. `npm test`, `npm run build` и baseline guard проходят без новых fingerprints.
12. Нет M1.4 CRUD, production materials wiring, V0 shapes или новых dependencies.
13. Документы репозитория и Obsidian совпадают по относительным путям и SHA-256.

# Ручной smoke

Когда доступен корректно установленный Electron runtime с native `better-sqlite3`:

1. открыть копию существующей `flow.db` версии 3;
2. убедиться, что приложение применило marker 4 и сохранило legacy memory row;
3. повторно открыть ту же копию;
4. проверить `quick_check = ok` и отсутствие повторной миграции.

Нельзя выполнять smoke над единственной пользовательской БД. Отсутствие Electron binary/native binding в текущем checkout фиксируется в отчёте, а не исправляется скрытым `npm rebuild`.

# Итог реализации

- Существующие миграции 1–3 без изменения SQL перенесены в единый чистый manifest; добавлена глобальная версия 4 `materials-version-store-foundation`.
- Общий runner проверяет непрерывность manifest и применённой истории, отклоняет неизвестную future schema, выполняет каждую миграцию как `BEGIN IMMEDIATE → up → marker → COMMIT` и полностью откатывает ошибку.
- Создан типизированный `DatabaseMigrationError` с номером, именем и исходной причиной. `db.ts` выполняет `quick_check` до и после migration runner, закрывает неуспешно открытый handle и не запускает rename/recreate исправного файла при логической ошибке миграции.
- Миграция 4 создаёт только `materials_projects` и append-only `materials_object_versions`, четыре предметных индекса, same-project predecessor FK, project FK и два триггера запрета `UPDATE`/`DELETE`.
- SQLite проверяет object JSON, положительную целочисленную `entity_revision`, уникальный `(project, contract, entity, revision)`, lowercase SHA-256, существование проекта, predecessor того же проекта и запрет самоссылки. Список 44 контрактов не продублирован в SQL.
- Fresh database получает markers 1–4. Физическая копия v3 сохраняет legacy memory/meta rows и прежние `applied_at`, получает только marker 4 и проходит `quick_check`.
- Повторный запуск идемпотентен. Тестовая падающая v4 на физической копии не оставляет DDL, DML или marker; исходный v3-файл остаётся побайтово неизменным по SHA-256.
- После первого независимого ревью закрыты две проблемы: дробная SQLite revision и поздняя классификация физической порчи. Финальный read-only аудит не обнаружил P1/P2-блокеров.
- Финальные проверки: M1.3 12/12, targeted + baseline 15/15, весь проект 19 test-файлов и 607/607 тестов; production build прошёл, новых TypeScript fingerprints нет.
- Test-only `node:sqlite` исполнил один и тот же production SQL на SQLite 3.50.3. Native Electron smoke не выполнен: текущий checkout не содержит Electron binary и `better_sqlite3.node`; скрытый rebuild, способный сменить ABI, не производился.
- Единственное отложенное P3-усиление — сверять уже применённый marker 4 с `sqlite_master` против ручной порчи. Штатная атомарная миграция не может записать marker без DDL.
- V0-shapes, payload migrations, M1.4 repository CRUD, M1.5 events, IPC и Knowledge Plane не создавались. Карточка готова к приёмке; M1.4 автоматически не запускается.
