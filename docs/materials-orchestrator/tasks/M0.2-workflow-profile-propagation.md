# Цель

Передать одно и то же проверенное значение `WorkflowProfile` через всю существующую цепочку запуска:

`renderer-нода → preload → main IPC → root WorkerData → worker → engine`.

Профиль должен присутствовать в каждой опубликованной записи trace и принудительно наследоваться подоркестраторами. Старая нода без поля профиля продолжает работать как `generic`.

M0.2 только переносит и журналирует профиль. Разделение путей исполнения относится к M0.3.

# Зависимость

M0.1 принята владельцем и имеет статус `accepted`. Канонический контракт находится в `src/shared/orchestrator/workflowProfile.ts` и в M0.2 не изменяется.

# Зачем это нужно

До появления отдельного материаловедческого маршрута все слои должны видеть одно и то же значение. Иначе renderer может показать один профиль, worker получить другой, подоркестратор потерять профиль родителя, а журнал не сможет объяснить, в каком режиме был создан результат.

# Нормативные имена

- На границах запуска: `workflowProfile`.
- В машинно-читаемой записи trace: `workflow_profile`.
- Тип везде импортируется как `WorkflowProfile` из общего модуля M0.1.
- Ручное дублирование union `'generic' | 'materials_rnd'` запрещено.

# Входит в задачу

1. Добавить опциональное сохранение `workflowProfile` в `shape.props.extra` orchestrator-ноды.
2. Показать минимальный выбор `Обычный` / `Материаловедческий` в существующих настройках ноды.
3. Для старой ноды без поля показывать и передавать `generic` без миграции доски.
4. Передать поле через `window.flow.orchStart` и preload без преобразования.
5. Проверить недоверенный IPC-вход в main через Zod и канонический контракт M0.1 до создания run, Vault-записи и Worker.
6. Сделать поле обязательным внутри `WorkerData` и `OrchestrateOpts`.
7. Централизованно добавлять профиль ко всем trace-записям на границе worker.
8. Создать начальную запись trace в main до запуска Worker, чтобы даже ошибка создания процесса имела профиль запуска.
9. Наследовать профиль ребёнком из доверенного родительского `WorkerData`; не принимать его из `spawnSub`-сообщения агента.
10. Сохранять профиль вместе с новым деревом задач.
11. Добавить чистые production-адаптеры только там, где они нужны для безопасного тестирования границ без запуска Electron.

# Не входит в задачу

- разветвление engine по профилю;
- materials state machine и `materials:*` IPC;
- автоматический выбор профиля по тексту или флагу `sci`;
- блокировка `webBuildPhase` или lecture-builder;
- изменения research, planner, mode selector, modes и registry;
- новые агенты, инструменты, RAG или научные модели;
- миграция старых досок;
- исправление сторонних TypeScript-ошибок;
- сборка установщика.

# Инварианты

## Старая нода

```text
workflowProfile отсутствует
→ renderer показывает generic
→ main назначает generic
→ WorkerData и engine получают generic
→ trace.workflow_profile = generic
```

## Материаловедческий профиль

```text
workflowProfile = materials_rnd
→ значение проходит без изменения
→ на M0.2 выполняется прежний engine
→ отдельный маршрут появится только в M0.3
```

## Ошибка

```text
workflowProfile = materials
→ main возвращает ok: false
→ projectId, run и Worker не создаются
→ неизвестное значение не превращается в generic
```

## Рекурсия

```text
родитель = materials_rnd
→ spawnSub не содержит поля профиля
→ main копирует доверенное значение родителя
→ ребёнок = materials_rnd
```

# Критерии приёмки

1. Старые ноды запускаются как `generic` без миграции.
2. Renderer сохраняет и передаёт оба допустимых значения.
3. Preload не теряет и не меняет поле.
4. Main независимо валидирует вход; invalid отклоняется до побочных эффектов.
5. `WorkerData.workflowProfile` и `OrchestrateOpts.workflowProfile` обязательны.
6. Root и все child WorkerData получают профиль своего run и не смешиваются с другим run.
7. Каждая опубликованная и сохранённая trace-запись содержит `workflow_profile`.
8. Даже ранний выход engine оставляет начальный trace.
9. Новое дерево задач содержит профиль.
10. M0.2 не добавляет условной маршрутизации и не меняет generic-путь.
11. Позитивные, отрицательные, inheritance, trace и generic-regression тесты проходят.
12. `npm test` и `npm run build` проходят.
13. В изменённых файлах нет новых TypeScript-ошибок относительно baseline.

# Ручной smoke

1. Открыть старую orchestrator-ноду без профиля: показывается `Обычный`.
2. Запустить короткую задачу: trace содержит `generic`.
3. Выбрать `Материаловедческий`: значение сохраняется в ноде.
4. Запустить задачу: trace содержит `materials_rnd`, но выполняется прежний engine.
5. Вернуть `Обычный` и убедиться, что значение сохраняется.

Реальный рекурсивный LLM-запуск не обязателен: наследование проверяется детерминированным тестом.

# Поведение при ошибке

- Unknown-профиль не получает fallback.
- Main не создаёт частичный run.
- Worker и ребёнок не могут изменить профиль.
- Ошибка профиля показывается как ошибка запуска.
- Ошибка trace не разрешает переключить профиль run.

# Отчёт о выполнении — 2026-08-28

Карточка реализована, проверена и принята владельцем перед началом M0.3.

## Что реализовано

- В настройках orchestrator-ноды появился выбор `Обычный` / `Материаловедческий`.
- Старая нода без поля профиля безопасно получает `generic`.
- Renderer проверяет и нормализует профиль перед вызовом preload.
- Main повторно проверяет недоверенный IPC-вход через Zod до создания `projectId`, записей Vault и Worker.
- `workflowProfile` стал обязательным внутри `WorkerData` и `OrchestrateOpts`.
- Root Worker получает проверенное значение, а child Worker наследует его только от доверенного родителя.
- Начальный trace создаётся в main до запуска Worker; все последующие worker-trace централизованно получают `workflow_profile`.
- Новое дерево задач сохраняет `workflow_profile`.
- Маршрутизация engine не менялась: оба профиля пока используют прежний путь исполнения.
