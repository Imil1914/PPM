# Цель

Создать синхронный project-scoped repository поверх таблиц M1.3. Repository сохраняет валидированные версии материаловедческих объектов, разрешает только точные `VersionRef`, выдаёт ограниченную историю и создаёт следующую версию без изменения предыдущей строки.

M1.4 закрывает только четыре операции: `create`, `read`, `list`, `supersede`. Она не подключает repository к IPC, renderer, engine или агентам.

# Принятые архитектурные решения

## Единый persistable manifest

Единственным manifest допустимых `contract_id` служит `materialsV1ContractRegistry`. Отдельный ручной allowlist не создаётся: все 44 принятых M1.1-контракта могут быть payload сохраняемой версии.

Тринадцать контрактов являются вложенными структурами и не имеют собственного `schema_version`. Они всё равно могут получать точный `VersionRef`, когда становятся самостоятельным объектом знания. Поэтому физически сохраняется не голый payload, а обязательный storage envelope:

```ts
type StoredMaterialsVersion<Name extends MaterialsV1ContractName> = {
  record_id: EntityId
  project_id: EntityId
  schema_version: Name
  id: EntityId
  version: number
  payload: MaterialsV1ContractOutput<Name>
  payload_sha256: string
  supersedes_ref: VersionRef | null
  created_at: IsoDateTime
  created_by: ActorRef
}
```

Этот envelope реализует общее правило сохранённого объекта из документа 04. Если нормативный payload сам объявляет `schema_version`, `id`, `version`, `project_id`, `created_at` или `created_by`, значение обязано точно совпасть с envelope. Контракт никогда не угадывается по форме payload.

## Точная адресация и изоляция

`VersionRef` не содержит `project_id`, поэтому каждая операция получает обязательный project context. Все SQL-запросы начинают область поиска с `project_id`. Ссылка из другого проекта выглядит как отсутствующая и не раскрывает существование чужой строки.

`entity_id` стабилен на всей линии версий. `create` создаёт только revision 1. `supersede` принимает точную текущую ссылку и создаёт только `N+1` того же `(project, contract, entity)`.

# Публичный API

Repository реализуется как чистый модуль без Electron import и принимает минимальный структурный SQLite adapter с `exec` и `prepare/get/all/run`.

```ts
create(input): StoredMaterialsVersion
read({ projectId, ref }): StoredMaterialsVersion
list({ projectId, contractId, entityId, beforeVersion?, limit? }): VersionPage
supersede(input): StoredMaterialsVersion
```

- `read` разрешает только exact revision; latest alias и автоматический переход по predecessor запрещены.
- `list` охватывает один exact `(project, contract, entity)`, сортируется newest-first, использует exclusive `beforeVersion`, `limit + 1` и возвращает `nextBeforeVersion`.
- `limit` по умолчанию 50, допустимый диапазон 1–100; offset pagination отсутствует.
- `record_id` генерируется repository. `createdAt` можно передать явно; если он отсутствует, repository использует инъецируемые часы. Контракт с собственным `created_at` передаёт тот же timestamp в payload и input, поэтому вызывающий код не угадывает внутреннее время.
- Проект должен существовать заранее. M1.4 не создаёт проект и не меняет его статус/`updated_at`.

# Валидация записи

До открытия write-транзакции:

1. Проверить `projectId`, `contractId`, `entityId`, `ActorRef`, явный или сгенерированный ISO UTC timestamp, cursor и limit нормативными boundary-схемами.
2. Потребовать exact key `materialsV1ContractRegistry`.
3. Выполнить `schema.parse(payload)` именно выбранного контракта.
4. Сверить все присутствующие identity/audit поля payload с будущим envelope.
5. Выполнить существующую рекурсивную `canonicalizeMaterialsJson`.
6. Сериализовать compact JSON, выполнить JSON round-trip и повторную Zod-валидацию, чтобы write-return и последующее read были эквивалентны, включая `-0`.
7. Рассчитать lowercase SHA-256 от точных UTF-8 байтов compact canonical JSON.

`create` отвергает payload с присутствующим `supersedes_id`. При `supersede` это поле, если оно существует в контракте, обязано ссылаться на стабильный logical `id` предшественника. Физической истиной lineage остаётся `supersedes_record_id`.

# Валидация чтения

Каждая строка, полученная через `read` или `list`, проверяется fail closed:

1. тип и допустимость всех SQLite-колонок, включая safe integer revision;
2. известный `contract_id` и project scope;
3. JSON parse и object root;
4. равенство сохранённого текста compact canonical JSON;
5. пересчитанный SHA-256;
6. нормативный Zod parse;
7. совпадение payload/envelope;
8. корректность predecessor той же линии для revision `N > 1`.

Повреждённая строка делает ошибочной всю операцию; repository не пропускает её молча. Возвращаемые envelope и payload являются отделёнными от БД и рекурсивно замороженными.

# Транзакции и конкурентность

Обе write-операции используют собственную транзакцию `BEGIN IMMEDIATE → checks → INSERT → COMMIT`, а при ошибке — `ROLLBACK`.

`create` внутри lock проверяет существование проекта и отсутствие любой revision линии.

`supersede` внутри одного lock:

1. проверяет проект;
2. разрешает точного predecessor в том же project;
3. проверяет contract/entity/revision и, если передан, expected hash;
4. проверяет, что predecessor является единственной head и не имеет child;
5. вычисляет только `N+1`;
6. вставляет строку с `supersedes_record_id = predecessor.record_id`;
7. фиксирует транзакцию.

Повторный writer со старым ref получает conflict. Если внешняя запись уже создала несколько children или нарушила same-line/N+1, это corruption, а не обычный conflict. Ни одна операция repository не выполняет `UPDATE` или `DELETE`; триггеры M1.3 остаются вторым барьером.

# Ошибки

Локальный `MaterialsVersionRepositoryError` содержит стабильный `code`, операцию, project context, необязательный ref и внутреннюю cause. В публичное сообщение не попадают SQL, путь БД, payload, stack или raw SQLite text.

Минимальные коды:

- `INVALID_ARGUMENT`;
- `UNKNOWN_CONTRACT`;
- `PAYLOAD_VALIDATION_FAILED`;
- `PAYLOAD_ENVELOPE_MISMATCH`;
- `PAYLOAD_NOT_JSON`;
- `PROJECT_NOT_FOUND`;
- `VERSION_NOT_FOUND`;
- `VERSION_ALREADY_EXISTS`;
- `VERSION_CONFLICT`;
- `RECORD_ID_COLLISION`;
- `STORAGE_CORRUPTION`;
- `STORAGE_FAILURE`.

Mapping в `StructuredFailureV1` остаётся M1.6.

# Критерии приёмки

1. `create` сохраняет valid canonical revision 1 и возвращает точный envelope/`VersionRef`.
2. Все 44 registry contracts проходят динамическую create/read matrix; 31 payload с собственным `schema_version` сверяются с contract ID, 13 без него адресуются внешним envelope.
3. Unknown contract, неверная Zod shape, custom refinement и каждый metadata mismatch отклоняются до INSERT.
4. Неканонизируемый JSON, `undefined`, `BigInt`, `Date`, cycle, `NaN` и прочие не-JSON значения не приводят к строке.
5. `read` разрешает exact project-scoped ref и повторно проверяет canonical JSON, SHA-256, Zod и envelope.
6. Ссылка из другого проекта возвращает `VERSION_NOT_FOUND`; глобального read по `record_id` нет.
7. `list` работает newest-first, bounded keyset pagination не создаёт duplicate/skip при добавлении новой head между страницами.
8. `supersede` создаёт ровно `N+1` с физическим predecessor; старая строка и её байты не изменяются.
9. stale/non-head ref, second child, revision gap, другая contract/entity/project линия и expected hash mismatch отклоняются атомарно.
10. Два repository instances с одним stale predecessor создают максимум одну `N+1`; второй получает conflict.
11. Повреждённые напрямую строки: неизвестный contract, неверный JSON/hash/Zod/envelope/lineage или unsafe revision — `STORAGE_CORRUPTION`; list не скрывает повреждение.
12. Возвращённый вложенный объект нельзя изменить; повторный read остаётся неизменным.
13. Ошибка ID collision или INSERT откатывает транзакцию; публичная ошибка не раскрывает SQLite internals.
14. Raw `UPDATE`/`DELETE` прежней версии по-прежнему запрещены триггерами.
15. Тот же production SQL исполняется настоящей временной SQLite через test-only `node:sqlite`; новая dependency и native rebuild отсутствуют.
16. Полный `npm test`, `npm run build` и M0.6 baseline проходят без новых fingerprints.
17. Generic profile не импортирует repository и не получает нового поведения.
18. Документы репозитория и Obsidian совпадают по относительным путям и SHA-256.

# Итог реализации

- Создан изолированный синхронный `versionRepository.ts` без Electron import и production wiring. Он экспортирует типизированные envelope/input/page/error-типы, класс repository и фабрику для минимального SQLite adapter.
- Единственным persistable manifest остаётся существующий реестр всех 44 контрактов. Динамический тест доказывает его точное совпадение с 44 M1.1 fixtures и разделение на 31 payload с собственным `schema_version` и 13 payload, адресуемых только внешним envelope.
- `create` создаёт только revision 1, `read` разрешает exact project-scoped `VersionRef`, `list` выдаёт bounded newest-first keyset page, `supersede` создаёт только `N+1` того же logical entity. Глобального read, latest alias, update и delete API нет.
- Write metadata согласуется без гонки времени: вызывающий код может передать проверенный `createdAt`, а при его отсутствии используется инъецируемый clock. Совпадающие поля payload строго сверяются с envelope.
- После Zod parse payload канонизируется, проходит compact JSON round-trip, повторный Zod parse и получает lowercase SHA-256 от точных UTF-8 байтов. Read/list заново проверяют SQLite-колонки, safe integer revision, canonical bytes, hash, Zod и envelope.
- `create` и `supersede` выполняются через `BEGIN IMMEDIATE`; stale hash/ref, второй child, record collision и неожиданный INSERT полностью откатываются. Старые строки остаются побайтово прежними, а triggers M1.3 продолжают запрещать raw `UPDATE`/`DELETE`.
- Полная lineage загружается двумя project-scoped пакетными запросами: один для непрерывных ancestors `1..N`, второй self-join для всех child-связей. В памяти проверяются predecessor record IDs, contract/entity, `N+1`, gaps, branches и неизвестные/повреждённые children; число синхронных SQLite round-trips не зависит от depth.
- Реальная test-only SQLite покрыла 45/45 M1.4 cases: все 44 контракта, явный timestamp с default production clock, project isolation, canonical/hash/`-0`, non-JSON, metadata mismatch, exact read, cursor pages, stale writers через два handles, corruption, unsafe int64, rollback, immutable output, raw triggers и физическое reopen.
- Полный regression: 20 test-файлов и 652/652 теста. M0.6 baseline: 3/3. `npm run build` и `git diff --check` прошли.
- Первое независимое code review выявило два дефекта: невозможность надёжно согласовать repository-owned timestamp и повторные lineage-запросы `O(page × depth)`/`O(depth)` round-trips. Оба исправлены. Два финальных read-only аудита bulk-lineage и отдельный acceptance-аудит не обнаружили P1/P2.
- Native Electron/`better-sqlite3` smoke не выполнен: checkout по-прежнему не содержит `electron.exe` и `better_sqlite3.node`. Скрытый rebuild ABI не выполнялся; общий production SQL проверен `node:sqlite` на физических временных файлах.
- M1.5 events, M1.6 failure mapping, project CRUD, IPC, renderer, engine, agents, Knowledge Plane, новая migration/dependency и generic behavior не затронуты. Карточка переведена в `review`; M1.5 автоматически не запускается.
