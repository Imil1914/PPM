# AGENTS.md — правила работы над PPM

Этот файл обязателен для Codex и других инженерных агентов, работающих в репозитории. Его цель — сделать изменения предсказуемыми, проверяемыми и согласованными с продуктовой архитектурой.

## 1. Цель проекта

PPM — система интеллекта проекта для нескольких команд. Она объединяет:

- Plane Community как внутренний движок управления работой;
- оболочку и дизайн-язык AntyFlow/PPM;
- Project Canvas как визуальный граф проекта;
- Project Vault для Markdown и файлов;
- Project Brain для RAG, графа знаний и памяти;
- Git provider для repositories, commits и pull requests;
- AI-агентов, работающих через preview, approval и audit.

Текущий код — desktop-прототип AntyFlow. Не предполагай, что целевая web-архитектура уже реализована.

## 2. Приоритет источников

При конфликте используй следующий порядок:

1. явное последнее указание владельца в текущей задаче;
2. ближайший к изменяемому файлу `AGENTS.md`;
3. этот корневой `AGENTS.md`;
4. карточка текущей задачи в `docs/project-spec/Документация PPM/Intelligence-first/tasks/`;
5. каноническое ТЗ `docs/project-spec/Документация PPM/Intelligence-first/`;
6. существующие контракты, миграции и тесты;
7. историческая документация — только как контекст, не как инструкция.

Редакции `web-first v1` и `Plane-first v2` имеют статус `superseded`. Не реализуй их очередь параллельно с Intelligence-first.

## 3. Обязательный стартовый чек-лист

Перед изменениями:

1. прочитай `README.md`;
2. прочитай этот файл полностью;
3. открой канонический `docs/project-spec/Документация PPM/Intelligence-first/README.md`;
4. открой `tasks/README.md` и карточку назначенной задачи;
5. проверь фактический `git status`, текущую branch и remotes;
6. найди ближайшие реализации и тесты через `rg`/`rg --files`;
7. проверь зависимости карточки и не считай их выполненными только по статусу в Markdown;
8. зафиксируй короткий план и список предполагаемых файлов;
9. проверь, нет ли пользовательских незакоммиченных изменений в той же области;
10. если задача требует внешнего write, credentials, публикации или разрушительного действия — убедись, что это явно разрешено.

Если карточка не названа, выбери только первую `ready` задачу из актуальной очереди. Не начинай несколько карточек одновременно.

## 4. Неподвижные архитектурные правила

Нельзя нарушать следующие инварианты без отдельного принятого ADR:

1. Пользователь видит PPM/AntyFlow, а не визуально узнаваемый Plane.
2. Plane владеет auth, workspace, projects, Work Items, Cycles, Modules, Views и Pages.
3. Project Vault владеет папками, Markdown, PDF и проектными файлами.
4. Canvas хранит расположение, визуальные связи и ссылки-проекции; он не создаёт вторую базу задач, документов или Git-объектов.
5. Project Brain index является производным и полностью перестраивается из источников.
6. Любой retrieval фильтруется по `workspace_id`, `project_id` и правам пользователя до ранжирования.
7. Код, branches, commits и pull requests принадлежат Git provider.
8. PPM не реализует собственный Git protocol, object store или merge engine.
9. AI не выполняет write без preview, явного approval, проверки версии и audit trail.
10. Plane закрепляется на точной версии/commit; production не зависит от плавающей upstream branch.
11. AGPL notices и доступ к соответствующему исходному коду нельзя скрывать ребрендингом.
12. Удаление Canvas projection не удаляет её source entity.

## 5. Границы каталогов

```text
src/main/          trusted Electron process, filesystem, DB, IPC, agents
src/preload/       минимальный typed bridge; не раскрывать произвольный Node API
src/renderer/src/  untrusted UI; не хранить secrets и не обращаться к fs напрямую
sync-server/       отдельный real-time сервис
docs/              техническая и продуктовая документация
docs/project-spec/ полный экспорт требований и исполнительных карточек
```

Новый web-контур Plane/PPM добавляется только в структуру, принятую задачей I0.1. Не раскладывай новые сервисы случайно по desktop-каталогам.

## 6. Рабочий процесс

Для каждой задачи:

1. **Discover** — проверь реальный код, типы, тесты, конфиги и ограничения.
2. **Bound** — выпиши scope, non-goals, зависимости и критерии приёмки карточки.
3. **Design** — определи источник истины, контракты, ошибки и rollback.
4. **Implement** — делай минимальное целостное изменение без попутного рефакторинга.
5. **Verify** — выполни проверки карточки и релевантные regression tests.
6. **Review** — просмотри diff на secrets, лишние файлы, дублирование и незаявленное изменение поведения.
7. **Document** — обнови документацию только там, где изменились факты или контракт.
8. **Report** — перечисли результат, изменённые файлы, проверки, риски и следующий шаг.

Карточки проходят `planned → ready → in_progress → review → accepted`. Агент может предложить `review`, но `accepted` устанавливает только владелец после демонстрации.

## 7. Правила изменения кода

- Сохраняй существующий стиль TypeScript/React и включённый `strict`.
- Не используй `any`, отключение type checking или пустой `catch` для обхода ошибки без объяснённой причины.
- Все входы на trust boundary валидируй схемой или явной проверкой.
- Ошибки должны быть типизированы либо нормализованы в стабильный публичный контракт.
- UI-строки размещай в i18n, если затрагиваемый экран уже использует локализацию.
- Не размещай бизнес-логику Plane в Canvas renderer.
- Не выполняй filesystem, shell или provider operations напрямую из renderer.
- Не меняй публичный API, persisted schema или event payload без versioning/migration.
- Derived data должно содержать `source_version`, `content_hash` или эквивалентный признак актуальности.
- Для фоновой обработки предусматривай idempotency, retry policy и dead-letter/reconciliation путь.
- Новая зависимость требует объяснения: зачем она нужна, почему существующего пакета недостаточно и каковы её license/security последствия.
- Не делай массовое переименование, форматирование или обновление зависимостей внутри функциональной задачи без прямой необходимости.

## 8. Данные и миграции

- Любая project-scoped запись содержит и проверяет `workspace_id` и `project_id`.
- Foreign keys, unique constraints и индексы являются частью контракта, а не последующей оптимизацией.
- Миграция должна быть детерминированной, повторяемой в чистой базе и совместимой с rollback policy.
- Не исправляй production-like данные ручными запросами вместо миграции.
- Удаление по умолчанию не должно разрушать audit/history, если карточка не требует hard delete.
- RAG/vector/cache данные считаются производными; первичные файлы и сущности должны переживать их полное удаление.

## 9. Безопасность

Никогда не коммить:

- `.env` и локальные конфиги;
- API keys, OAuth tokens, cookies и private keys;
- реальные пользовательские документы или дампы БД;
- signed URLs;
- сырые webhook payload с секретами;
- содержимое `%APPDATA%/Flow`;
- `node_modules`, `out`, `release`, sidecars и другие воспроизводимые артефакты.

Обязательные свойства:

- deny by default;
- авторизация на server/trusted boundary, а не только скрытие кнопки;
- project isolation до retrieval/search;
- проверка webhook signature и защита от replay;
- redaction secrets в логах;
- path normalization и запрет traversal для Vault;
- sanitize потенциально активного SVG/HTML;
- preview/approve/audit для AI write actions.

При обнаружении секрета остановись, не публикуй его и сообщи владельцу только путь и тип риска, не значение.

## 10. Проверки

Минимум для затронутого desktop-кода:

```bash
npm test
npm run build
```

Для узкой итерации допускается сначала запустить конкретный Vitest-файл, но перед завершением задачи выполни полный релевантный набор.

Дополнительно по типу изменения:

- migration: clean migration + повторный запуск + rollback/restore сценарий;
- API/event: contract, authorization, idempotency и invalid-input tests;
- Canvas: persistence, projection refresh, delete-source separation и browser safety;
- Vault: path traversal, version conflict, MIME/size и permission tests;
- RAG: cross-project isolation, citations, stale index и purge tests;
- Git: signature, replay, revoke, rate limit и duplicate event tests;
- UI: loading, empty, error, keyboard и reduced-motion состояния;
- deploy: clean checkout build, health checks и backup/restore smoke.

Не заявляй проверку пройденной, если команда не запускалась. В отчёте указывай точную команду и результат.

## 11. Документация

- Каноническая текущая редакция находится в `docs/project-spec/Документация PPM/Intelligence-first/`.
- Новое обязательное требование добавляй также в `20 — Матрица требований и трассировка.md`.
- Новую работу оформляй отдельной карточкой по `tasks/_TEMPLATE.md`.
- Принятое архитектурное изменение оформляй как ADR/decision с альтернативами, последствиями и rollback.
- Исторические документы не удаляй и не переписывай так, будто решение всегда было другим; помечай `superseded` и связывай с новым решением.
- README должен описывать фактическое состояние, а не только целевую картину.
- Если repository-копия документации расходится с Obsidian-vault, сообщи владельцу и предложи конкретную синхронизацию; не делай молча двусторонний merge.

## 12. Git и commits

- Перед работой проверь branch и `git status`.
- Не изменяй и не удаляй чужие незакоммиченные правки.
- Одна карточка должна давать один обозримый набор изменений.
- Формат сообщения: `<type>(<scope>): <результат>`, например `docs(ppm): publish intelligence-first specification`.
- Не используй `git reset --hard`, force-push, переписывание истории или удаление branch без явного разрешения.
- Не выполняй merge/rebase поверх неизвестных изменений молча.
- Перед commit просмотри staged diff и список новых файлов.
- Перед push убедись, что remote и branch соответствуют запросу владельца.
- Pull request должен содержать: цель, scope, non-goals, проверки, миграции, риски и rollback.

## 13. Запрещённые сокращения пути

Не допускается:

- копировать таблицы Work Items в PPM ради удобства UI;
- хранить файлы одновременно в Vault и Plane attachments без явного import/export provenance;
- добавлять «временный» общий RAG index для нескольких проектов;
- выполнять AI-generated изменения автоматически;
- подменять реальные интеграции iframe/webview без утверждённого решения;
- включать весь Plane `preview` как плавающую зависимость;
- писать собственный GitHub/Git server;
- выдавать mock или статический JSON за завершённый production flow;
- скрывать известную ошибку или непроведённую проверку в итоговом отчёте.

## 14. Когда нужно остановиться

Остановись и запроси решение владельца, если:

- задача требует новый внешний сервис, платный план или credential;
- нужно выбрать лицензию, LLM/embedding provider, vector backend или Git provider;
- меняется источник истины либо граница Plane/Vault/Canvas/Git;
- требуется удалить данные, переписать историю или выполнить force-push;
- обнаружены пересекающиеся пользовательские изменения;
- требования противоречат AGPL, безопасности или межпроектной изоляции;
- критерий приёмки невозможно проверить в доступном окружении;
- фактическая архитектура существенно расходится с карточкой.

До ответа можно выполнять только безопасные read-only проверки и готовить обратимое предложение.

## 15. Формат итогового отчёта агента

Итог должен коротко отвечать на вопросы:

1. Какой пользовательский результат получен?
2. Какие файлы и контракты изменены?
3. Какие команды проверки запущены и каков результат?
4. Что сознательно не входило в scope?
5. Какие риски или ручные действия остались?
6. Как выполнить rollback?
7. Какой следующий шаг по очереди?

Не заставляй владельца восстанавливать эту информацию из журнала команд.
